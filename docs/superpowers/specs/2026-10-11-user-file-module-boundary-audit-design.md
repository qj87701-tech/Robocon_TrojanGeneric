# User_File 模块边界审查与整理设计

## 1. 目标

对 `User_File` 下全部手写源码进行模块边界审查，使代码继续保持中科大 USTC RoboWalker 的直接、易对照风格，同时明确区分：

- 头文件中的跨模块公开接口；
- 源文件中的模块私有实现；
- 中科大参考代码；
- 第三方协议源码；
- 当前工程新增或适配的代码。

本次整理重点解决头文件接口过度公开、源文件私有符号缺少内部链接、实现专用常量位于头文件、以及测试直接依赖内部实现等问题。

## 2. 成功标准

- 每个 `.h` 只公开调用方实际需要的类型、宏、对象和函数。
- 每个 `.cpp` 的内部变量和辅助函数具有文件内部链接。
- 保留中科大文件头、分区注释、命名、对象组织和回调布局。
- 第三方源码可以被完整检查，但不因风格统一而被重写。
- 不改变电机控制、底盘解算、协议数据、调度周期、参数或安全逻辑。
- 相关主机测试、全部主机测试和 Debug 固件构建通过。

## 3. 已确认的参考行为

本机中科大 DM02/RoboWalker 参考工程的 `tsk_config_and_callback` 采用以下组织方式：

- `.h` 放置 `Exported` 类型、变量和函数声明；
- `.cpp` 包含实现所需头文件；
- `.cpp` 保留 `Private macros`、`Private types`、`Private variables` 和 `Private function declarations` 分区；
- 私有实现不会为了形式统一而搬到 `.h`。

因此本次整理不会机械地把包含指令、宏、整数类型或函数声明全部移动到头文件，而是依据是否跨模块使用决定位置。

## 4. 来源分组

### 4.1 中科大参考与移植模块

包括但不限于：

- `1_Middleware/Algorithm/Basic`

- `1_Middleware/Driver/UART`
- `1_Middleware/System/Timestamp`
- `2_Device/Motor/Motor_DM`
- `2_Device/Plotter/Vofa`

处理原则：保持参考结构，只修复当前移植或扩展造成的接口边界问题，不进行现代化重写。

### 4.2 第三方协议与芯片定义

包括：

- `1_Middleware/Hipnuc`
- `2_Device/NRF24L01/nrf24l01_define.h`
- 其他带有明确第三方版权或协议布局的定义文件

处理原则：检查编译边界、包含关系和调用方式，但不做格式化重排，不改变结构体布局、宏值、报文定义或上游接口。

### 4.3 当前工程新增或适配模块

包括但不限于：

- `1_Middleware/Protocol/pro_sbus`
- `2_Device/IMU/HI06`

- `3_Module/Chassis/Omni`

- `4_Task` 下全部任务模块

处理原则：完整审查公开接口、私有链接、头文件依赖、类型归属和中科大风格一致性。

## 5. 统一边界规则

### 5.1 头文件

头文件只包含以下内容：

- 头文件保护宏；
- 公开接口自身所需的最小包含；
- 跨模块使用的宏、枚举、结构体、类和回调类型；
- 跨模块使用的对象 `extern` 声明；
- 跨模块调用的函数声明。

如果公开声明使用 `uint8_t`、`uint16_t` 等类型，头文件应直接或通过明确依赖获得对应定义，不能依赖调用方碰巧先包含其他文件。

### 5.2 源文件

源文件保留以下内容：

- 仅实现需要的头文件；
- 仅本模块使用的宏和常量；
- 私有类型；
- 私有对象、状态和缓冲区；
- 私有辅助函数声明及定义。

文件内部变量和自由函数使用 `static` 保持内部链接。继续采用中科大的 `Private` 分区和直接控制流程，不引入匿名命名空间、管理器、模板框架或配置系统。

### 5.3 必须保持全局的符号

以下符号不能因为整理而错误设为 `static`：

- STM32 HAL 要求的回调入口；
- C协议库对外函数；
- 被其他模块真实引用的设备对象和状态；
- 通过驱动注册的公开回调类型和驱动入口；
- `Task_Init()`、`Task_Loop()`等生产调度入口。

## 6. 分层整理设计

### 6.1 `1_Middleware`

- 保留中科大算法、CAN、UART和时间戳模块的文件组织。
- HAL回调函数保持外部链接。
- 驱动内部过滤器配置、辅助函数和内部缓冲区仅在确认没有外部依赖后收紧。
- HiPNUC C源码维持上游形式，不进行C++风格改造。

### 6.2 `2_Device`

- 类、公开枚举、公开结构和调用方需要的成员接口保留在 `.h`。
- 协议打包、字节序转换、固定控制报文和内部状态留在 `.cpp`。
- DM、VOFA等参考模块优先保持原结构。
- VESC和HI06适配重点检查实现专用包含及内部辅助函数。

### 6.3 `3_Module`

- 底盘类、轮组枚举和调用方需要的数据类型保留在 `.h`。
- 解算辅助函数及仅模块内部使用的阈值放在 `.cpp`。
- `SWERVE_MOTION_ENTER_SPEED`、`SWERVE_MOTION_EXIT_SPEED`当前只在 `mod_chassis_swerve.cpp` 使用，应移至该源文件。

### 6.4 `4_Task`

- 头文件只公开初始化入口、周期入口、必要诊断结构和真实跨任务对象。
- CAN/UART转发回调、内部周期回调、通道换算和任务内部控制函数留在 `.cpp` 并设为 `static`。
- 不改变裸机前台调度方式，不引入RTOS、队列或SUBS。

## 7. 已确认的任务层调整

### 7.1 `tsk_config_and_callback`

- `Key1`、`Key2`、调度Tick及按键历史状态改为文件私有。
- CAN1、CAN3、UART4、UART9转发回调改为文件私有。
- 各周期内部回调改为文件私有。
- `Task_Init()`、`Task_Loop()`继续公开。
- `init_finished`因CAN和UART驱动仍在使用而继续保持跨模块可见。

### 7.2 `tsk_remote`

- 通道换算和指令更新函数改为文件私有。
- `SBUS_Receive`在确认没有生产代码跨模块访问后改为文件私有。
- `NRF24L01`与`Remote_Chassis_Command`继续公开，因为其他任务存在真实引用。

### 7.3 `tsk_motor_init`

- `Motor_Init()`继续公开。
- `Motor_Omni_Init()`、`Motor_Swerve_Init()`、`Motor_VESC_Init()`仅由本模块生产代码调用，应收回源文件。
- 现有直接调用分项初始化函数的测试改为通过正式公开入口验证，不为测试在生产头文件中保留内部接口。
- DM和VESC对象继续公开，因为底盘、回调和调试任务均有真实引用。

### 7.4 `tsk_chassis`

- 全向轮控制、电机发送、失能、舵向和行进控制辅助函数改为文件私有。
- `Chassis_Swerve_Control()`生产代码只在本模块使用，应收回源文件。
- 现有测试改为通过正式周期入口驱动控制流程。
- 初始化、周期入口和跨调试模块使用的诊断数据继续公开。

### 7.5 `tsk_debug`

- 当前VOFA状态、轮组指针、数据缓冲区和格式转换函数已经采用文件私有形式，保留该组织。
- 仅配置任务实际调用的初始化、接收和周期入口，以及外部需要主动选择或打印的接口保留在 `.h`。

## 8. 测试接口处理

生产头文件不能仅因为主机测试方便而公开内部函数。测试应优先通过真实公开入口观察行为：

- 电机初始化测试通过 `Motor_Init()`验证默认选择和对象配置；
- 舵轮任务测试通过正式周期回调进入控制链路；
- CAN/UART测试通过注册得到的函数指针触发接收回调；
- 不向生产类增加仅用于测试的接口。

若某项内部行为无法通过公开入口可靠观察，应先判断测试是否过度依赖实现；只有确实属于公共能力时才保留或新增公开接口。

## 9. 风险控制

- 不修改CAN ID、报文布局、控制模式、量程和单位。
- 不修改舵轮解算、传动比、斜坡、PID、死区和遥控映射。
- 不修改任务周期和回调注册顺序。
- 不修改电机默认失能和通信超时保护。
- 不更改CubeMX生成文件。
- 不批量格式化第三方或中科大参考源码。
- 每次收紧符号前必须通过全工程引用搜索确认没有生产调用方。

## 10. 验证策略

遵循Native验证纪律：

1. 每完成一个独立层级，运行与该层级直接相关的主机测试。
2. 不在每次小修改后重复完整固件编译。
3. 全部模块整理完成后运行全部现有主机测试。
4. 最后执行一次 `build/Debug` 完整固件编译和链接，目标为 `Robocon-Elian.elf`。
5. 检查编译器和链接器是否发现缺失声明、重复符号或头文件依赖问题。
6. 软件验证通过后明确说明尚未完成物理板回归。

## 11. 非目标

- 不重构电机、底盘、遥控或调试功能。
- 不修改VESC官方固件或FOC算法。
- 不统一所有命名或替换现有中科大命名体系。
- 不新增RTOS、队列、SUBS、服务类或通用框架。
- 不处理与模块边界无关的参数调优和硬件问题。
- 不创建Git分支、提交或Pull Request。

## 12. 完成标准

- `User_File`全部手写模块均已按来源完成审查并形成修改或保留结论。
- 明确的私有符号不再泄漏到其他翻译单元。
- 头文件不存在仅为内部实现或测试而公开的接口。
- 第三方及中科大参考模块的可对照性得到保留。
- 主机测试与Debug固件构建通过。
- 最终列出所有修改文件、保留未改文件的原因以及尚需硬件验证的事项。
